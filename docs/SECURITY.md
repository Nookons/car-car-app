# Безопасность и защита данных

Стандарт: OWASP ASVS Level 2 (приложение с личными данными, без платежей) +
RODO (польская реализация GDPR). Документ — не «пожелания», а список решений,
которые входят в код с первой фазы.

## Что мы защищаем

| Актив | Почему важен | Где |
|---|---|---|
| Аккаунты и сессии | доступ к подпискам и истории | Telegram `initData` → JWT |
| Подписки и фильтры | поведение человека, косвенно — его интересы | Postgres |
| История уведомлений | кто что искал и когда | Postgres (90 дней) |
| Инфраструктура | бот, БД, сервер | VPS, секреты |
| Репутация | блокировка площадкой = смерть продукта | сборщик |

**Чего у нас нет — и это главная мера защиты:** телефонов продавцов
(на otomoto они зашифрованы), паспортных данных, платёжных данных, адресов
доставки, переписки с продавцами. Меньше данных — меньше последствий утечки.

## Модель угроз

| Угроза | Вектор | Мера |
|---|---|---|
| Подделка входа | чужой `initData` / повтор перехваченного | HMAC-подпись бота, `auth_date` ≤ 300 с, кэш хэшей от повтора |
| Кража сессии | XSS, утечка токена | JWT 15 мин, refresh с ротацией, привязка к устройству, httpOnly не нужен (токен в памяти), CSP |
| IDOR | подмена `user_id`/`listing_id` в запросе | `user_id` только из токена, никогда из тела; проверка владения |
| Нагрузка/абьюз | скрипт дёргает API | rate limit по пользователю и IP, лимит подписок, капча не нужна (Telegram) |
| Инъекции | SQL, HTML в описании объявления | параметризованные запросы, санитайзер HTML при записи и выводе |
| SSRF | подстановка URL фото | allowlist хоста CDN, запрет редиректов на приватные IP |
| Утечка секретов | коммит `.env`, логи | gitleaks в CI, секреты только в env, редакция логов |
| Компрометация зависимости | npm/pip пакет | lock-файлы, `pip-audit`/`npm audit`, Dependabot, минимальный набор зависимостей |
| Скрейпинг нас | кто-то качает нашу БД через API | лимиты, пагинация ≤ 50, отсутствие «выгрузить всё» |
| Блокировка площадкой | слишком агрессивный сбор | rate limit 1 req/s, backoff, уважение 429/403 |

## Аутентификация

1. Mini App присылает `Telegram.WebApp.initData` (строка `query_id=...&hash=...`).
2. Сервер проверяет:
   - `hash` = HMAC-SHA256(secret, data_check_string), где
     `secret = HMAC_SHA256("WebAppData", bot_token)`;
   - `auth_date` не старше **300 секунд**;
   - хэш не встречался раньше (Redis, TTL 10 минут) — защита от повтора.
3. Выдаём пару: `access` (15 мин, JWT HS256) + `refresh` (30 дней, случайный,
   в БД только SHA-256).
4. Refresh ротируется при каждом использовании; повторное использование
   старого refresh → отзыв всей цепочки (признак кражи).
5. Выход — отзыв refresh; смена языка/настроек сессию не трогает.

Паролей, e-mail и SMS-кодов нет. Это осознанно: единственный фактор —
Telegram, и он же идентификатор.

## Авторизация

- Каждый запрос скоупится пользователем из токена; поле `user_id` в теле
  запроса **игнорируется** (иначе IDOR).
- Роли: `user`, `admin`. Админ-действия — только через отдельный роутер,
  с записью в `audit_log` (кто, что, когда, из какого IP/устройства).
- Пользователь видит только свои подписки/избранное/уведомления; чужие id
  возвращают `404`, а не `403` (не подтверждаем существование).

## Защита API

- Валидация — Pydantic v2, strict-режим, лимиты: пагинация ≤ 50, длина строк,
  допустимые значения фильтров (allowlist, не «любой SQL»).
- Ошибки — по контракту [`PRODUCTION.md`](PRODUCTION.md): `application/problem+json`,
  никаких стектрейсов и SQL в ответе.
- Rate limit: 60 запросов/мин на пользователя, 300/мин на IP, 10/мин на
  `/auth/*`; ответ `429` + `Retry-After`.
- CORS: только домен Mini App; CSP `default-src 'self'`; никаких `eval`.
- Идемпотентность: `Idempotency-Key` для операций, создающих сущности
  (подписка, жалоба), TTL 24 часа.
- Размер тела ≤ 64 КБ, таймауты 5 с, заголовок `X-Request-Id` в каждом ответе.

## Приватность (RODO)

### Какие данные храним и зачем

| Данные | Зачем | Основание | Срок | Где |
|---|---|---|---|---|
| `tg_id`, `username`, `first_name` | аккаунт, адресация сообщений | договор | до удаления | Postgres |
| `lang`, настройки | работа сервиса | договор | до удаления | Postgres |
| критерии подписок | основная функция | договор | до удаления | Postgres |
| уведомления (id объявления, время) | доставка, разбор жалоб | законный интерес | 90 дней | Postgres |
| просмотренные id | дедупликация | законный интерес | 14 дней | Redis |
| объявления площадок | продукт | законный интерес | пока активно + 30 дней | Postgres |
| логи приложения | безопасность | законный интерес | 30 дней | файлы/коллектор |
| бэкапы | восстановление | законный интерес | 30 дней | Storage Box, шифруются |

**Не храним:** телефоны продавцов, имена частных продавцов, переписку,
платёжные данные. Для дилеров храним название и публичный URL профиля —
это данные компании, не физлица.

### Права пользователя — прямо в боте

| Право | Как | Срок исполнения |
|---|---|---|
| Доступ | `/privacy` → что храним и зачем | сразу |
| Экспорт | `/export` → JSON со всеми данными | сразу (файл в чат) |
| Удаление | `/delete` → подтверждение → мягкое удаление | 30 дней, затем purge-джоб |
| Отзыв согласия | отключение уведомлений | сразу |

Удаление — каскадное: аккаунт, подписки, избранное, история уведомлений.
Объявления (публичные данные площадки) остаются, персональных данных в них нет.

### Процессоры и передача

| Процессор | Что | Локация | Документ |
|---|---|---|---|
| Hetzner | сервер, БД, бэкапы | EU (Германия/Финляндия) | DPA |
| Telegram | доставка сообщений | вне EU | SCC + DPA |
| Sentry (EU-регион) | ошибки | EU | DPA |
| Домен/почта | DNS, поддержка | EU | DPA |

Список процессоров — публичная страница; изменение списка = обновление
политики. Данные за пределы EU не вывозим, кроме Telegram (SCC).

### Инцидент

- Классификация: P0 — утечка ПДн или полная недоступность; P1 — частичная;
  P2 — деградация.
- При подтверждённой утечке ПДн — уведомление UODO **в течение 72 часов**,
  пользователям — без неоправданной задержки.
- Runbook: локализовать → отозвать ключи → оценить объём → уведомить →
  postmortem без поиска виноватых.

### До публичного запуска

- Политика конфиденциальности и Условия — на 4 языках, ссылки в боте и Mini App.
- Скрининг DPIA: вероятно не требуется (минимум данных, нет профилирования
  с юридическими последствиями), но решение фиксируем письменно.
- Проверка: `/privacy`, `/export`, `/delete` работают и проверены тестом.

## Секреты и инфраструктура

- Секреты — только в переменных окружения (Docker secrets / `EnvironmentFile`),
  `.env` локально, в git — `.env.example` без значений.
- CI: `gitleaks` на каждый PR; при находке — блок сборки.
- Ротация: токен бота — раз в квартал и при любом подозрении; пароль БД —
  при смене состава.
- Доступ к серверу: только SSH-ключи, без пароля, `fail2ban`, отдельный
  пользователь для деплоя, root — запрещён.
- БД: отдельный пользователь приложения с минимальными правами (без `SUPERUSER`,
  без `CREATEDB`), миграции — отдельной ролью.
- Шифрование: TLS 1.2+ (Caddy), шифрование диска VPS, бэкапы — `age`-ключом.
- Firewall: снаружи только 80/443 и SSH по ключу; Postgres/Redis — только
  внутри docker-сети.

## Логи

- Структурированный JSON, `request_id`, `user_id` (хэш), `route`, `status`, `ms`.
- **Не логируем:** `initData`, токены, телефоны, полные URL с параметрами
  авторизации.
- Ошибки — в Sentry с PII-фильтром (телефоны, e-mail, токены вырезаются).
- Доступ к логам — только у владельца; срок хранения 30 дней.

## Чек-лист перед публичным запуском

- [ ] `initData` валидируется, `auth_date` и replay проверяются
- [ ] refresh-ротация и отзыв работают
- [ ] ни один эндпоинт не принимает `user_id` из тела
- [ ] rate limit включён и проверен нагрузочным тестом
- [ ] HTML из объявлений санитизируется (XSS-тест с `<img onerror>`)
- [ ] секреты не в git (gitleaks), `.env` в `.gitignore`
- [ ] бэкап снимается, шифруется и **восстановление проверено**
- [ ] `/privacy`, `/export`, `/delete` работают
- [ ] политика и условия опубликованы на 4 языках
- [ ] SSH только по ключу, пароль root отключён
- [ ] Sentry не содержит PII
- [ ] зависимости без критических уязвимостей

## Что не делаем (и почему)

- **2FA/пароли** — не нужны, вход только через Telegram.
- **Собственный OAuth-сервер** — избыточно, Telegram уже даёт идентичность.
- **Шифрование полей в БД** — при нашем наборе данных (нет телефонов, нет
  платёжных данных) это создаёт ложное чувство защиты и мешает работе.
  Шифруем диск и бэкапы.
- **SOC2 / ISO 27001** — сертификация стоит десятки тысяч и не даёт ничего
  продукту на этом этапе. Стандарты соблюдаем, сертификат — нет.
- **Пентест до запуска** — вместо него ASVS-чеклист и внешний аудит после
  первых платных пользователей.
