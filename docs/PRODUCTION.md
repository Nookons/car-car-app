# Прод-стандарт: надёжность, ошибки, наблюдаемость, поддержка

Требование: «уровень серьёзной биг-тех компании». В переводе на практику это
значит: измеримые SLO, единый контракт ошибок, наблюдаемость по умолчанию,
предсказуемые релизы, восстановление после сбоя и поддержка, которая отвечает.
Это не про количество процессов, а про то, что каждый сбой виден и имеет
владельца.

Важная оговорка: **биг-тех — это стандарты, а не численность.** Копировать
Kubernetes, Kafka и 24/7 NOC на одного человека — способ не запустить продукт
никогда. Ниже — то, что реально влияет на качество, и отдельно — что сознательно
не делаем.

## SLO

| Что | Цель | Как меряем | Бюджет ошибки |
|---|---|---|---|
| Доступность API | **99.5%/мес** | 5xx / всего запросов, синтетическая проверка раз в минуту | 3 ч 39 мин в месяц |
| Латентность API (список) | p95 < 300 мс | гистограмма по роутам | — |
| Латентность API (карточка) | p95 < 150 мс | то же | — |
| Доставка уведомления | p95 «увидели → отправили» < 15 с | `detected_at`/`sent_at` | — |
| Успешность доставки | ≥ 99.5% | Telegram ok / попытки | — |
| Свежесть сбора | p95 задержка поллинга < 20 с; нет «слепых» окон > 10 мин в рабочее время | `crawl_run`, алерт | — |
| Дубли пушей | 0 | `unique(user_id, listing_id, kind)` + сверка | — |

SLO — не «цель на будущее», а то, по чему строятся алерты. Превысили бюджет
ошибок за месяц — следующий спринт идёт на надёжность, а не на фичи.

## Контракт ошибок

Единый формат для API (RFC 9457, `application/problem+json`):

```json
{
  "type": "https://carcar.app/errors/subscription-limit",
  "title": "Subscription limit reached",
  "status": 409,
  "code": "subscription_limit_reached",
  "detail": "Maximum 10 active subscriptions",
  "trace_id": "01J9Z4K3Q8",
  "errors": [
    {"field": "criteria.price_max", "code": "too_large", "message": "Max 5 000 000 PLN"}
  ]
}
```

| Код | HTTP | Когда | Ретрай клиентом |
|---|---|---|---|
| `auth_missing` / `auth_invalid` | 401 | нет/битый токен, плохой `initData` | нет, перелогин |
| `auth_expired` | 401 | истёк access | да, через refresh |
| `forbidden` | 403 | роль | нет |
| `not_found` | 404 | чужой/несуществующий id | нет |
| `validation_failed` | 422 | поля | нет, исправить |
| `rate_limited` | 429 | лимит | да, после `Retry-After` |
| `conflict` | 409 | дубль, идемпотентность | нет |
| `subscription_limit_reached` | 409 | лимит подписок | нет |
| `upstream_unavailable` | 503 | otomoto/Telegram недоступны | да, с backoff |
| `internal` | 500 | всё остальное | 1 раз |

Правила: наружу не уходят стектрейсы, SQL и имена таблиц; в каждом ответе —
`X-Request-Id`, он же в логах и в тексте для поддержки. В боте ошибка
показывается человеческим текстом на языке пользователя + кнопка «Поддержка»
с готовым `trace_id` — человек не должен объяснять, что случилось.

## Надёжность

- **Таймауты** на любой внешний вызов: 5 с (API), 10 с (сбор), 15 с (Telegram).
- **Ретраи** — только идемпотентные операции: экспоненциальный backoff с полным
  джиттером, максимум 3 попытки. Мутирующие запросы — с `Idempotency-Key`.
- **Circuit breaker** на otomoto и Telegram: 5 ошибок за 30 с → размыкание на
  60 с, половина-открытое состояние для проверки.
- **Dead letter queue**: сообщение не доставлено после ретраев → `failed` +
  запись с причиной, а не бесконечный цикл.
- **Деградация**: не работает Telegram → пуши в очередь, данные собираются;
  не работает otomoto → бот отвечает «сбор приостановлен», а не врёт пустотой;
  не работает БД → API отдаёт 503 с `Retry-After`, бот — заглушку.
- **Graceful shutdown**: SIGTERM → перестаём принимать, доигрываем очередь,
  закрываем пул.
- **Health**: `/healthz` (жив) и `/readyz` (БД, Redis, Telegram) — разные
  проверки, Docker перезапускает только по `/healthz`.

## Наблюдаемость

**Логи** — JSON, обязательные поля: `ts`, `level`, `request_id`, `user_hash`,
`route`, `status`, `duration_ms`, `code`. Ротация 30 дней, без PII.

**Метрики** (Prometheus):
- RED по API и по боту: rate, errors, duration;
- сбор: `poll_total`, `poll_errors`, `poll_lag_seconds`, `new_listings`,
  `fresh_ratio`;
- очереди: `queue_depth{name}`, `dlq_depth{name}`;
- БД: соединения, медленные запросы (>200 мс), размер;
- бизнес: подписки, отправленные пуши, конверсия «пуш → клик».

**Трейсы** — OpenTelemetry на запрос: API → БД, collector → parse → match →
Telegram. Одна трасса на объявление даёт видимый путь «где потерялись секунды».

**Дашборды**: «Сбор», «Уведомления», «API», «Инфраструктура». Один экран на
вопрос «работает ли сейчас и что болит».

**Алерты** — только те, по которым есть действие:

| Алерт | Порог | Действие |
|---|---|---|
| Нет новых объявлений | 0 за 10 мин в рабочее время | проверить вёрстку/блокировку |
| Ошибки поллинга | > 5% за 15 мин | backoff, проверить 429/403 |
| Очередь пушей растёт | > 100 и растёт 5 мин | проверить Telegram, воркер |
| API 5xx | > 1% за 5 мин | инцидент |
| Диск | > 85% | чистка/расширение |
| Бэкап не снялся | 1 пропуск | инцидент |

Алерты идут в Telegram (личный чат владельца) и дублируются в почту.

## Ошибки пользователя: UX, а не только код

- В Mini App — экран ошибки с человеческим текстом, `trace_id` и кнопкой
  «Повторить», а не пустой белый экран.
- В боте — «Не получилось сохранить подписку. Попробуйте ещё раз» + код,
  а не «Internal Server Error».
- Формы валидируются на клиенте **и** на сервере; ошибки полей — по-польски
  и по-украински, не по-английски.
- Оффлайн в Mini App: показываем кэш и баннер «нет связи», не крутим вечный
  спиннер.

## Загрузки файлов

Сейчас пользовательских файлов в продукте нет, но политика нужна до первого
«а можно загрузить фото машины?»:

- Загрузка **только через presigned URL** (S3-совместимое хранилище, EU),
  API не принимает файлы через себя — нет нагрузки и нет обхода лимитов.
- Лимиты: 10 МБ, 5 файлов на объект, 20 в сутки на пользователя.
- Проверки: MIME по содержимому, а не по расширению; перекодирование
  изображений (Pillow) с удалением EXIF/GPS; антивирус (ClamAV) для всего,
  что не картинка; лимит пикселей (защита от «decompression bomb»).
- Хранение: приватный бакет, доступ по подписанным URL с TTL 15 мин,
  превью — через CDN.
- Админ-импорт CSV (например, справочник моделей): dry-run, валидация,
  отчёт об ошибках, откат по `import_id`.

## Нагрузка и ёмкость

| Поток | Объём | Запас |
|---|---|---|
| Опрос выдачи | 7 200 запросов/сутки, ~2 ГБ | один процесс, 4 параллельных запроса |
| Карточки | 5–7 тыс./сутки | очередь, 2 воркера |
| API | 100 DAU × 200 запросов = 20 тыс./сутки | 1 vCPU хватает с 10× запасом |
| Пуши | 7 тыс. новых × 1.2 подписки ≈ 8.4 тыс./сутки | < 1 сообщения/с в среднем |
| БД | 257 тыс. объявлений ≈ 1 ГБ + история | до 10 млн строк — всё ещё один Postgres |

Масштабирование по порядку: индексы → вертикально (8 vCPU) → разнести
collector/API/bot по процессам → отдельный хост под БД. Только после этого —
реплики и партиционирование. Kafka и шардирование на этих числах — вред.

## Поддержка

| Канал | Что | SLA |
|---|---|---|
| `/help` в боте | FAQ на языке пользователя | мгновенно |
| Кнопка «Поддержка» | тикет с `trace_id`, языком, версией | P0 — 4 ч, P1 — 24 ч, P2 — 72 ч |
| Статус-страница | доступность и инциденты | обновление в течение 30 мин |
| Обратная связь | 👍/👎 на уведомлении | метрика, раз в неделю разбор |

Тикеты — в Telegram-топик (или Lark, как в эко-системе), с шаблонами ответов
на 4 языках. Каждый инцидент P0/P1 заканчивается коротким postmortem:
что случилось, сколько длилось, что чиним, чтобы не повторилось.

## Процесс разработки

- **Trunk-based**: короткие ветки, PR, ревью, squash-merge. Conventional commits.
- **CI-гейты** (без них merge запрещён): линт, типы, unit, интеграционные
  (testcontainers), контрактные тесты парсера на фикстурах, миграции dry-run,
  `gitleaks`, `pip-audit`/`npm audit`.
- **Staging** — отдельный контур с урезанным набором данных; релиз сначала туда.
- **Миграции** — expand/contract: сначала добавить, потом переключить код,
  потом удалить старое. Обратная совместимость на время релиза.
- **Фича-флаги** для всего, что меняет поведение уведомлений.
- **Откат** — предыдущий образ по SHA, без «пересборки на месте».
- **Версионирование API** — `/v1`, ломающие изменения только в `/v2`.

## Бэкапы и восстановление

- Postgres: WAL-архив (RPO ≤ 1 ч) + ежедневный `pg_dump` (хранится 30 дней),
  шифрование `age`, выгрузка в другое хранилище (не на тот же диск).
- **Восстановление проверяется раз в месяц** на staging, с замером RTO.
  Непроверенный бэкап — это не бэкап.
- Цели: RPO ≤ 1 ч, RTO ≤ 4 ч.
- Redis — не источник истины: потеря = перечитать состояние из БД.

## Runbooks (короткие, в репозитории)

1. «Площадка отдаёт 403/429» — снизить темп, проверить IP, включить backoff.
2. «Нет новых объявлений» — проверить фикстуру, `__NEXT_DATA__`, алерт.
3. «Очередь пушей встала» — Telegram 429/5xx, проверить токен, DLQ.
4. «БД не отвечает» — диск, соединения, медленные запросы, перезапуск.
5. «Диск заполнен» — логи, WAL, старые бэкапы; временное расширение.
6. «Утечка секрета» — ротация токена, отзыв сессий, разбор логов.

## Что не делаем

Kubernetes, service mesh, Kafka, мультирегион, собственный кластер БД,
24/7 дежурство, SOC2, кастомная платформа метрик, микросервисы «на будущее».
На 1–2 человека и 257 тыс. объявлений всё это даёт стоимость без пользы.
Вернёмся, когда будет 10× нагрузка и команда.

## Влияние на сроки

Прод-каркас — не «после MVP», а часть MVP:

| Блок | Оценка |
|---|---|
| i18n-каркас + каталоги ([`I18N.md`](I18N.md)) | 1.5–2 дня |
| Контракт ошибок + обработчики в API/боте | 1 день |
| Auth (initData, JWT, refresh, rate limit) | 1.5 дня |
| Наблюдаемость (логи, метрики, Sentry, дашборд) | 1.5 дня |
| CI/CD, staging, бэкапы, runbooks | 1.5–2 дня |
| Политика/условия/`/privacy`/`/export`/`/delete` | 1 день |
| **Итого** | **+1.5–2 недели** |

MVP вырастает с ~2.5 до **5–6 недель**. Это честная цена «уровня биг-теха»:
без этих блоков продукт работает, но первый же инцидент или жалоба на данные
превращаются в ручную археологию.
