# Жизненный цикл объявления и «Индекс ушедших»

Документ описывает фундамент под «Индекс ушедших» (Q3 плана 2027): учёт
момента снятия, лёгкий архив и `dom_days` — сколько объявление было активно.
Продуктовая часть (оценка «уйдёт за N дней», сравнение, торг) сюда не входит;
это следующий слой.

## Зачем

Сейчас `status = 'removed'` почти не выставляется автоматически: `mark_removed()`
срабатывает только на 404/410 при `enrich`, а полный `sweep` исчезнувшие
объявления не помечает. Плюс `carcar_purge()` удаляет снятые через 30 дней.
Без этого «сколько машина висела до снятия» посчитать не из чего.

Терминология важна: снятие — не обязательно продажа. Объявление могло истечь,
быть снято продавцом или перевыставлено. Поэтому в коде и в отчётах —
`removed` / `off_market`, а не `sold`.

## Как определяется снятие

Полный `sweep` проходит все страницы выдачи. После завершения прохода:

1. `sweep_state.pass_started_at` — граница «видели в этом проходе».
2. Всем активным объявлениям с `last_seen_at >= pass_started_at` ставится
   `missed_sweeps = 0`.
3. Всем активным с `last_seen_at < pass_started_at` — `missed_sweeps += 1`.
4. Кто пропущен `MISSES_TO_REMOVE` (2) полных прохода подряд — получает
   `status = 'removed'`, `removed_at = now()` и событие `listing_event('removed')`.

Два пропуска защищают от ложного снятия, если одна страница выдачи не
открылась. Дополнительно проход не подтверждает снятия, если:

- он прерван `--max-pages`, `--minutes` или авто-паузой;
- `total_pages` неизвестен или пройдено меньше страниц;
- ошибок больше 1% страниц (`MAX_SWEEP_ERROR_RATIO`).

Плюс суточный grace (`REMOVAL_GRACE_DAYS`): объявление не снимается, если его
видели меньше суток до старта прохода. Выдача otomoto динамическая — за
многочасовой обход активная карточка может «перескочить» страницу; grace
отсекает такие ложные снятия. Реально старые записи (последний раз видели
неделю назад) он не защищает и они уходят как обычно.

При сомнении счётчики не трогаются — следующий чистый проход всё исправит.

`mark_removed()` (404/410) снимает сразу, без двух проходов: площадка прямо
сказала, что объявления нет.

## Что хранится

`listing`:

- `removed_at` — когда подтвердили снятие (не когда реально продали);
- `missed_sweeps` — сколько полных проходов подряд не видели.

`listing_lifecycle` — лёгкий снимок, переживает `carcar_purge()`:

| Поле | Смысл |
|---|---|
| `first_price` / `last_price` | первая известная и последняя цена |
| `price_changes` / `price_change_pct` | сколько раз менялась цена и на сколько % (минус — подешевело) |
| `dom_days` | дни от `published_at`/`first_seen_at` до **последнего наблюдения** |
| `dom_basis` | `published_at` или `first_seen_at` — от чего считали |
| `removed_at` | момент подтверждения снятия |
| `removal_kind` | `disappeared` (sweep), `gone_404`, `legacy` (старые данные) |

`dom_days` — нижняя оценка: от появления до последнего наблюдения. Верхняя
граница — `removed_at`, но она зависит от расписания sweep. Точность — интервал
полного обхода (обычно сутки).

## Почему архив, а не просто увеличить ретенцию

Полная строка `listing` содержит фото-массивы, описание и оборудование —
это дорого хранить годами. `listing_lifecycle` — только характеристики, цены и
даты. Поэтому `carcar_purge()`:

1. переносит подтверждённые снятые в `listing_lifecycle`;
2. удаляет полную строку `listing` через `retention_days` (по умолчанию 30);
3. хранит архив 730 дней.

`listing_lifecycle.listing_id` — без FK: архив должен жить дольше объявления.
Пишутся только подтверждённые снятия (`removed_at is not null`), чтобы
админское «скрыть» не попало в статистику.

## Деплой

Порядок важен: код пишет `removed_at` и `listing_lifecycle`, поэтому сначала
миграция, потом деплой.

```bash
psql "$DATABASE_URL" -f db/migrations/20261117_listing_lifecycle.sql
psql "$DATABASE_URL" -f db/migrations/20261118_listing_outcome.sql
# триггер на listing; применять, когда sweep не пишет
psql "$DATABASE_URL" -f db/migrations/20261119_listing_restore_cleanup.sql
```

Миграция 17 идемпотентна: добавляет колонки, создаёт архив, переносит уже
снятые (`removal_kind = 'legacy'`) и заменяет `carcar_purge()`. На больших
базах backfill может занять минуты — в миграции стоит `statement_timeout = 120s`.
18 добавляет `outcome`/`outcome_reason` и размечает `legacy`; 19 — триггер
очистки при возврате объявления.

## Расписание

`python -m carcar sweep` после завершения прохода сам вызывает
`reconcile_removed()`. Повторный проход не начинается раньше
`--min-interval` минут (в `scripts/run_collector.sh` и `entrypoint.sh` —
`CARCAR_SWEEP_MIN_INTERVAL`, по умолчанию 1440).

Ручной запуск:

```bash
python -m carcar sweep --from-page 1          # новый проход сейчас
python -m carcar sweep --min-interval 0       # без паузы между проходами
```

## Первые данные (12.11.2026)

После миграции в архив попали **1 128** старых снятых (`legacy`). Картина:

| Показатель | Значение |
|---|---|
| `dom_days`, p50 | 29.5 дня |
| `dom_days`, p90 | 30.0 дня |
| 15–30 дней | 930 из 1 128 |
| 7–14 дней | 148 |
| 0–6 дней | 19 |
| 31–60 дней | 31 |
| `price_change_pct = 0` | 1 128 из 1 128 |

Это похоже не на продажи, а на **истечение 30-дневного размещения**: почти все
снятия укладываются в 30 дней, цена ни у кого не менялась. Поэтому «Индекс
ушедших» нельзя строить как «медиану до снятия» — получится медиана срока
размещения. Для продуктового слоя нужен признак сделки:

- короткий `dom_days` (например, меньше 14–20 дней) как кандидат в продажу;
- падение цены перед снятием (`price_change_pct < 0`);
- перевыставление с тем же VIN/фингерпринтом — это не продажа;
- либо явный статус «продано» с площадки, если он появится.

Детектор уже собирает все ингредиенты для такого классификатора; сам классификатор
— следующий слой, не этот.

## Классификация снятий (outcome)

Площадка не отдаёт «продано», поэтому в `listing_lifecycle` есть эвристика:

| `outcome` | Когда | Смысл |
|---|---|---|
| `sold_candidate` | цена падала перед снятием (≤ −3%) | кандидат в продажу/торг |
| `expired` | 28+ дней и цена не менялась | почти наверняка истёк срок размещения |
| `unknown` | сигнала не хватило | не выдумываем продажу |

Заполняется при архивировании (`_archive_lifecycle`). Для старых `legacy`-строк
правило применено задним числом: **897 expired, 231 unknown** (на 13.11.2026).
`unknown` — это не ошибка, а честный ответ: лучше не считать 30-дневное
истечение продажей.

## Возврат объявления (restore/relist)

Если объявление снова появилось в выдаче, его строка в `listing_lifecycle`
удаляется триггером `listing_restored_cleanup` при переходе `removed → active`.
Иначе «Индекс ушедших» считал бы активное объявление снятым. Триггер и чистка
уже накопившихся таких строк — миграция
[`20261119_listing_restore_cleanup.sql`](../db/migrations/20261119_listing_restore_cleanup.sql).

## Как проверить

```sql
-- сколько снятий и какая медиана срока
select count(*) as removed,
       percentile_cont(0.5) within group (order by dom_days) as dom_median,
       percentile_cont(0.9) within group (order by dom_days) as dom_p90
from listing_lifecycle
where removed_at > now() - interval '90 days'
  and removal_kind <> 'legacy';

-- распределение по маркам/моделям
select make, model, count(*) as n,
       round(avg(dom_days), 1) as dom_avg,
       round(avg(price_change_pct), 1) as price_change_avg
from listing_lifecycle
where removed_at > now() - interval '90 days'
group by 1, 2
having count(*) >= 10
order by n desc;

-- кто уже помечен, но ещё не в архиве
select count(*) from listing
where status = 'removed' and removed_at is not null
  and not exists (select 1 from listing_lifecycle x where x.listing_id = listing.id);
```

После первого полного прохода `removed` появится только у объявлений,
пропущенных **два** прохода. Если нужен один — временно уменьшить
`MISSES_TO_REMOVE`, но тогда растёт риск ложных снятий при сбое страницы.

## Ограничения

- `removed` ≠ продано; `legacy` — оценка задним числом.
- Точность `dom_days` — интервал полного обхода (обычно сутки).
- Перевыставление с другим `external_id` — отдельное объявление; дедуп по VIN
  появится позже.
- Если `listing_moderation` скрывает объявление, `removed_at` не ставится:
  оно всё ещё на рынке. Это осознанно.
