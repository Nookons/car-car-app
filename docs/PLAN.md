# CarCar — план v0.1

Агрегатор объявлений о продаже авто в Польше с уведомлениями в Telegram.
Документ — черновик архитектуры и плана работ; код начнётся после согласования
развилок в конце файла.

Дата: 05.11.2026. Разведка источников: [`SOURCES.md`](SOURCES.md).

---

## 1. Продукт за 30 секунд

Пользователь один раз настраивает фильтр («BMW 320d, 2015+, до 45 000 zł,
до 200 тыс. км, Мазовецкое воеводство») и получает в Telegram **пуш через
1–2 минуты после появления объявления**, с ценой, фото и оценкой «насколько
это ниже рынка». Всё, что нашлось, лежит в Mini App: лента, поиск, история
цены, избранное.

Ценность не в том, что мы «показываем объявления» — их показывает сам otomoto.
Ценность в трёх вещах:

1. **Скорость.** Хорошая машина по низкой цене уходит за часы. Кто увидел
   первым — тот позвонил первым.
2. **Оценка цены.** «Этот Passat на 18% ниже медианы по рынку с поправкой
   на пробег» — то, чего нет в уведомлениях площадки.
3. **Один канал.** Позже — несколько площадок в одной ленте, без дублей.

## 2. Границы MVP

**Делаем:**

- один источник — otomoto.pl (257 тыс. объявлений, данные отдаются без браузера);
- полный снимок рынка + инкрементальный сбор новинок каждые 2–3 минуты;
- нормализация характеристик в общую модель (марка, модель, год, пробег,
  топливо, КПП, кузов, мощность, объём, город/регион);
- подписки с фильтрами и push в Telegram;
- Mini App: лента, карточка, фильтры, избранное, история цены;
- оценка «ниже/выше рынка» по когорте.

**Не делаем в MVP (сознательно):**

- второй и последующие источники (OLX закрыт защитой, см. SOURCES.md);
- хостинг фотографий у себя (только ссылки на CDN площадки);
- чат с продавцом, звонки, проверка VIN, кредит/страховка;
- мобильные приложения, публичный SEO-сайт, оплата подписок;
- несколько стран.

## 3. Архитектура

```
                    ┌──────────────────────── VPS (Docker Compose) ────────────────────────┐
                    │                                                                     │
 otomoto.pl         │   collector (Python, cron/asyncio)                                  │
   HTML ────────────┼──►  discovery: /osobowe?order=created_at:desc  ──┐                  │
   (GET, 1 req/s)   │       detail:  /oferta/<id>.html                 │                  │
                    │                                                  ▼                  │
                    │                                            Postgres 16              │
                    │   normalizer ──► listing / vehicle / price     (jsonb, GIN, trgm)     │
                    │   deduper    ──► VIN + phash + отпечаток            │                │
                    │   stats      ──► медианы по когортам                │                │
                    │                                                     │                │
                    │   matcher ◄── subscription (критерии) ◄── FastAPI ◄─┼── Mini App      │
                    │      │                                              │   (React SPA)   │
                    │      ▼                                              │        │        │
                    │   notifier (aiogram) ──► Telegram Bot API ──────────┼────────┘        │
                    │                              ▲                      │                 │
                    │                              └── initData → JWT ────┘                 │
                    │   Redis: очередь, блокировки, rate-limit                            │
                    └─────────────────────────────────────────────────────────────────────┘
```

Поток одного объявления:

```
страница выдачи ──► upsert listing (source, external_id)
                        │
                        ├─ новый?        ──► забрать карточку (фото, описание, VIN)
                        ├─ изменилась цена? ──► listing_snapshot + триггер «цена упала»
                        └─ нет изменений?  ──► обновить last_seen, выйти
                        │
                        ▼
              нормализация → vehicle (характеристики)
                        ▼
              дедуп: VIN → phash фото → отпечаток (марка/модель/год/пробег/цена/город)
                        ▼
              deal_score = отклонение от медианы когорты
                        ▼
              matcher: какие подписки подходят → notification (уникальная)
                        ▼
              notifier: сообщение в Telegram (фото + кнопки)
```

Ключевое проектное решение: **`listing` и `vehicle` — разные сущности.**
`listing` — объявление на конкретной площадке (цена, URL, продавец, статус).
`vehicle` — кластер «это один и тот же автомобиль», в который могут входить
объявления с разных площадок. Даже когда источник один, кластер нужен:
дилеры перевыставляют машину, меняя цену и фото, и без кластера мы будем
слать пользователю одно и то же авто трижды.

## 4. Стек: что берём и почему

| Слой | Выбор | Почему именно так | Альтернатива и почему нет |
|---|---|---|---|
| Сбор и обработка | **Python 3.12** + `httpx` + `selectolax` | разбор HTML/JSON, нормализация, статистика — сильная сторона Python; у тебя уже прод на FastAPI, опыт переносится | Node/TS — единый язык с фронтом, но парсинг/аналитика беднее, а выигрыш только в «одном языке» |
| БД | **PostgreSQL 16** | 257 тыс. строк — это мало; `jsonb` для сырых данных, GIN/trgm для поиска, оконные функции для медиан, `pgvector` на будущее | Supabase эко-системы — **не берём**: чужая предметная область, лимиты, лишняя связанность; Elasticsearch — избыточен на этом объёме |
| API | **FastAPI** + Pydantic v2 | быстрый старт, автодокументация, asyncio | Django — тяжелее, ничего не даёт |
| Очередь | **Redis 7 + arq** | отправка уведомлений и ретраи; Redis же держит rate-limit и локи сбора | Celery — лишний брокер; Kafka — не на этом масштабе |
| Бот | **aiogram 3** | асинхронный, актуальный, хорошая обработка 429 | python-telegram-bot — тоже норм, но aiogram удобнее в FSM/WebApp |
| Mini App | **Vite + React 18 + TS + Tailwind** + `@telegram-apps/sdk-react` + TanStack Query + Recharts | внутри Telegram SSR не нужен и даже вреден: нужен быстрый старт и маленький бандл | Next.js — пригодится позже для публичного SEO-сайта, для TWA избыточен |
| Хостинг | **один VPS (Hetzner CX32, 4 vCPU / 8 ГБ / 80 ГБ)** + Docker Compose + Caddy | всё в одном месте, дешёво, полный контроль над IP и лимитами | Railway/Vercel — быстрее стартовать, но сборщику нужен стабильный IP и дешёвый трафик; Vercel для Mini App избыточен |

Два языка (Python + TypeScript) здесь оправданы: каждый на своём месте, стык —
один HTTP-контракт.

## 5. Модель данных (черновик)

Полный DDL — [`../db/schema.draft.sql`](../db/schema.draft.sql). Суть:

```
source ─┐
        ├─< listing >── vehicle ──< price_stat (когорты)
seller ─┘     │  │
              │  ├─< listing_snapshot   (история: цена, пробег, заголовок)
              │  ├─< listing_photo      (url, phash)
              │  └─< notification >── user ──< subscription
              └─< crawl_run (наблюдаемость)
```

Решения, которые важно зафиксировать сразу:

- **`listing.raw jsonb`** — сырой JSON площадки. Храним, потому что структура
  источника меняется, а переиграть историю без сырых данных нельзя.
  HTML-страницы **не храним** (13.7 ГБ на снимок) — только разобранный JSON.
- **История — append-only.** `listing_snapshot` пишется только при изменении
  (цена/пробег/заголовок/статус), а не на каждом обходе. Иначе 257 тыс. строк
  × 720 обходов в сутки = мусор.
- **Никаких `ON DELETE CASCADE` на историю.** Удаление подписки не должно
  уносить отправленные уведомления; удаление продавца — историю цен.
  `SET NULL` / `RESTRICT`.
- **Мягкое удаление объявлений:** `status` + `last_seen_at`, физически не удаляем.
  «Снято с продажи» — это событие, а не отсутствие строки.
- **Справочники марок/моделей** — свои таблицы с алиасами (`bmw`, `BMW`,
  `БМВ`), потому что площадки пишут по-разному, а фильтры и статистика должны
  сходиться.
- **`price_stat`** — материализованные медианы по когортам, пересчёт ночью.
  Считать медиану на каждый запрос ленты — верный способ положить БД.

## 6. Пайплайн сбора

| Шаг | Что делает | Частота | Объём |
|---|---|---|---|
| Discovery | страницы `/osobowe?order=created_at:desc` | каждые 2–3 мин днём, 15 мин ночью | 1–3 страницы |
| Detail | карточка объявления (фото, описание, VIN) | только для новых/изменённых | ~3–6 тыс./сутки |
| Full sweep | обход всего рынка (обновление `last_seen`, поиск снятых) | раз в сутки, 03:00 | 8 044 страницы, ~2.2 ч |
| Normalize | JSON → поля `vehicle` | на лету | — |
| Dedup | VIN → phash → отпечаток | на лету | — |
| Stats | пересчёт медиан по когортам | ночью + инкрементально | ~5–10 тыс. когорт |
| Match | подписки × новые объявления | на лету | — |
| Notify | отправка в Telegram | на лету | — |

Все запросы — 1 req/s, с ретраями и экспоненциальной паузой. Параллельность
наращиваем только после проверки, что площадка не начинает отдавать 429/403.

**Ловушка, которую уже видно в данных:** сортировка `created_at:desc` не строгая.
На первой странице из 32 объявлений **13 старше суток** (от 10.10 до 30.10), и они
идут вперемешку со свежими. Похоже на «поднятые»/продвигаемые объявления: дата
создания у них старая, а позиция — верхняя. Поэтому:

- инкремент нельзя останавливать «на первом знакомом id» и нельзя резать строго
  по дате — пропустим свежие, стоящие ниже старого «продвинутого»;
- правило остановки: **2 страницы подряд, где >90% id уже известны**;
- и всё равно раз в 2–3 минуты забираем 2–3 страницы целиком — upsert по
  `(source, external_id)` делает повтор безопасным.

## 7. Уведомления

Правила, без которых бот быстро превращается в спам и его выключают:

- **Одно объявление — одно уведомление на пользователя** (`unique(user_id, listing_id, kind)`).
- **Тихие часы** 23:00–07:00 Europe/Warsaw — копим в утренний дайджест.
- **Батчинг:** если по фильтру за 10 минут набежало больше 3 машин — одно
  сообщение «5 новых: BMW 320d до 45 000 zł» со списком, а не пять пушей.
- **Кнопки в сообщении:** «Открыть на площадке», «В избранное», «Скрыть»,
  «Похожие». Всё — без перехода в браузер.
- **Дедуп между источниками:** кластер `vehicle` не должен дать два пуша
  на одну машину с otomoto и OLX.
- **Лимиты Telegram:** ~30 сообщений/с на бота, 1/с в один чат; на 429 —
  `retry_after` и очередь, а не повтор в цикле.
- **Дайджест** вместо мгновенных пушей — переключатель в настройках.

Первая версия (личное пользование) — мгновенные пуши по 1–3 фильтрам.
Мультипользовательский режим включаем, когда появится второй живой пользователь.

## 8. Mini App

Экраны:

1. **Лента** — новые по моим фильтрам, «свежие сверху», бейдж «−18% к рынку».
2. **Поиск** — фильтры слева/сверху (Amazon-стиль: плитки, не таблица),
   счётчик «1–24 из 1 340», сортировка по цене/дате/отклонению.
3. **Карточка** — галерея, цена и график её истории, характеристики,
   «по рынку: 52 000–58 000 zł», продавец (частник/дилер), кнопка на площадку.
4. **Подписки** — список фильтров, вкл/выкл, «прислать тестовое уведомление».
5. **Избранное** — сохранённые авто, отметка «продано/снято».
6. **Настройки** — язык, тихие часы, дайджест vs мгновенно.

Авторизация: `Telegram.WebApp.initData` → проверка HMAC-SHA256 на бэкенде
(ключ — `HMAC_SHA256(bot_token, "WebAppData")`) → свой JWT на 30 дней.
Никаких паролей и email. В dev-режиме — флаг, разрешающий вход по фиксированному
`tg_id` только на localhost.

## 9. Аналитика цен — то, ради чего продукт существует

Просто показывать объявления умеет сама площадка. Мы добавляем оценку:

1. **Когорта:** марка + модель + поколение + год ±1 + топливо + КПП.
2. **Поправка на пробег:** внутри когорты регрессия `log(price) ~ mileage`
   (или медианы по корзинам пробега, если данных мало).
3. **Устойчивые статистики:** медиана и MAD вместо среднего (объявления-
   выбросы «1 zł» и «999 999 zł» не должны двигать оценку).
4. **Минимальный размер выборки:** n ≥ 25, иначе когорта расширяется
   (год ±2, затем только марка+модель). Мало данных — честно пишем «оценки нет»,
   а не выдумываем число.
5. **Deal score:** `(медиана_с_поправкой − цена) / MAD`. Порог «интересно» —
   настраиваемый, по умолчанию −15%.
6. **Дни в продаже:** от `first_seen`; быстрый рост срока + снижение цены =
   продавец готов торговаться (отдельный сигнал).

Это же считается по истории: «цена упала на 4 000 zł за 12 дней» — сильный пуш.

## 11. Право и этика

Это не юридическая консультация, но риски нужно назвать до кода:

- **robots.txt соблюдаем.** У otomoto страницы разрешены, `/api/` и `/ajax/` —
  запрещены; мы туда не ходим. У OLX `robots.txt` вообще не отдаётся — это
  сигнал «не пустят», а не «можно».
- **Защиту не обходим.** Если площадка показывает капчу/блокировку — не
  взламываем, а либо снижаем темп, либо идём через официальный API/партнёрство.
- **Минимум персональных данных.** Телефоны продавцов не сохраняем (на otomoto
  они и так зашифрованы), имена частных лиц не публикуем, дилеров — указываем
  как источник со ссылкой.
- **Не зеркалим контент.** У себя храним то, что нужно для поиска и уведомлений;
  фото — ссылками на CDN площадки; описание — сокращённо, с ссылкой на оригинал.
- **Атрибуция обязательна:** каждое объявление в Mini App ведёт на оригинал.
- **Официальный канал — цель, а не запасной вариант.** У OLX Group есть
  партнёрские фиды для агрегаторов; с ростом проекта это дешевле, чем война
  с антиботом, и снимает юридический риск.
- **Триггер на остановку:** письмо от площадки — останавливаем источник в тот
  же день, без «сначала докажем, что мы правы».

## 12. План по фазам

Оценки — в днях работы, не календарных.

### Фаза 0. Разведка и каркас — 0.5–1 день *(частично сделано)*
- [x] проверка otomoto: 200, 257 382 объявления, 32/стр, JSON в HTML
- [x] проверка OLX/Allegro/AutoScout24: блокировки, зафиксировано
- [x] скрипт-разведчик `scripts/probe_otomoto.py`
- [x] черновик схемы БД (`db/schema.draft.sql`)
- [ ] каркас репозитория: `docker-compose.yml`, `.env.example`, линтеры
- [ ] тест лимитов: 200 запросов подряд, замер 429/403

### Фаза 1. Сбор данных — 3–4 дня
- коллектор otomoto (discovery + detail), ретраи, rate-limit, лог `crawl_run`;
- нормализация в `vehicle` + справочники марок/моделей;
- дедуп v1 в пределах источника;
- CLI: `search`, `show`, `stats`;
- полный снимок рынка и замер: сколько реально новых объявлений в сутки.
- **Готово, когда:** полный обход отрабатывает без ошибок, повторный обход
  не создаёт дублей, цена/пробег/характеристики заполнены у >95% объявлений.

### Фаза 2. Бот и уведомления — 3–4 дня
- FastAPI: `/v1/listings`, `/v1/subscriptions`, `/v1/auth/telegram`;
- бот: `/start`, создание подписки по шагам, тестовое уведомление;
- matcher + notifier, тихие часы, дедуп отправок;
- деплой на VPS, systemd/Docker, бэкапы.
- **Готово, когда:** новое объявление по фильтру приходит в Telegram
  в среднем < 3 минут после публикации (проверяем на живом рынке сутки).

### Фаза 3. Mini App — 4–5 дней
- лента, карточка, фильтры, избранное;
- график истории цены;
- авторизация через `initData`;
- мобильная вёрстка, тёмная тема, скелетоны загрузки.
- **Готово, когда:** приложение открывается в Telegram на iOS и Android,
  лента листается без лагов на 10 тыс. записей (пагинация, не «всё сразу»).

### Фаза 4. Аналитика — 3–5 дней
- `price_stat` по когортам, поправка на пробег, deal score;
- алерты «цена упала», «ниже рынка на N%»;
- дайджест.
- **Готово, когда:** оценка есть у >60% активных объявлений, ручная проверка
  10 случайных карточек подтверждает адекватность медиан.

### Фаза 5. Расширение — после MVP
- второй источник (OLX через браузер/прокси или партнёрский фид);
- кросс-дедупликация (VIN/phash);
- мультипользовательность, оплата, лимиты тарифов;
- публичный SEO-сайт на Next.js (если нужен органический трафик).

## 13. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Площадка ужесточает защиту, 403 на VPS-IP | средняя | сборщик можно держать на домашней машине и слать в API; прокси; снижение темпа; официальный фид |
| Изменилась структура `__NEXT_DATA__` | высокая (раз в месяцы) | контрактные тесты на сохранённых фикстурах; алерт «0 объявлений за обход» |
| Юридические претензии по скрейпингу | средняя | минимум данных, ссылки на оригинал, не зеркалим контент, готовность выключить источник |
| Дубли между площадками | высокая при 2+ источниках | кластер `vehicle`, VIN, phash, отпечаток — проектируем с фазы 1 |
| Telegram 429 при массовых пушах | средняя | очередь, батчинг, `retry_after`, rate-limit на чат |
| Стоимость хранения растёт | низкая | HTML не храним, только JSON; снимки — по изменению |
| «Хорошие» машины уходят раньше пуша | средняя | инкремент каждые 2–3 мин в рабочее время; приоритет скорости в архитектуре |

## 14. Открытые вопросы (нужно решение до фазы 1)

1. **Кто пользователь?** Только ты и знакомые — или планируются платные
   подписчики? От этого зависят юридические риски, мультитенантность и
   требования к нагрузке.
2. **Что важнее в уведомлениях:** все новые по фильтру, только «ниже рынка
   на X%», или только падения цены? (Можно всё, но приоритет — разный.)
3. **Язык интерфейса:** польский, русский, украинский или переключатель?
4. **OLX нужен в MVP или можно начать с одного otomoto?** (OLX сейчас
   блокирует — это +браузер и +прокси, +€5–15/мес и +неделя работы.)

6. **География фильтров:** вся Польша или конкретные воеводства/радиус от
   города? (Влияет на геокодирование и на объём матчинга.)
7. **Перепродажа/выкуп авто** — если да, нужны инструменты сравнения и
   заметок по машине; если только поиск — не нужны.
