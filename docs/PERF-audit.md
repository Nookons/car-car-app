# Аудит производительности CarCar

Дата: 10.11.2026. Объём: статический аудит репозитория — Python Telegram-бот/сборщик, FastAPI Mini App API, Next.js веб-клиент, PostgreSQL/Redis и Railway-конфигурация — плюс ограниченные read-only проверки production PostgreSQL и публичных Railway/Vercel endpoints. Полная телеметрия, нагрузочная проверка и доступ к настройкам внешних хостингов отсутствовали. Поэтому отсутствие конфигурации в репозитории отмечено как «не подтверждено», а не как доказанный runtime-дефект.

## Краткий итог

Основа производительности уже хорошая: фотографии площадки запрашиваются в уменьшенном размере, есть серые плейсхолдеры и отложенная загрузка, поиск фильтруется с debounce, выдача постраничная, SQL формирует разные поля для карточки и списка, пул Postgres и Redis-кэш предусмотрены, а сборщик использует Brotli/keep-alive/таймауты. Есть серверная генерация метаданных карточки и ленивое получение следующей порции ленты.

После аудита добавлены in-flight dedupe для GET, Next Image с AVIF/WebP, сжатие Next, Cache-Control для хэшированных чанков и собственных изображений. Остаются: OpenTelemetry/RUM и измерения production; реальное подтверждение edge/CDN response headers; проверка внешних фотоформатов на слабой сети. Видеорежим ИИ и отдельное автодополнение в продукте не обнаружены. Railway относится к API/боту; веб-приложение деплоится на Vercel (см. `docs/MINIAPP.md`), поэтому CDN и компрессию веб-статики определяет также платформа.

## Приоритетные действия

1. **Добавить OpenTelemetry и RUM**: серверные route/DB spans, Web Vitals (LCP/INP/CLS), экспорт в доступный backend и алерты по p95. Сейчас это самый большой пробел наблюдаемости.
2. **Снять production response headers** (`Content-Encoding`, `Cache-Control`, `Age`, `Via`) и проверить, что правила Next не переписываются Vercel.
3. **Проверить изображения на реальном браузере**: `Content-Type` для AVIF/WebP, размеры transfer, fallback и кэш оптимизатора.
4. **Снять EXPLAIN (ANALYZE, BUFFERS)** для популярных фильтров/сортировок; менять индексы только по планам и реальной нагрузке.
5. **Проверить N+1 по SQL-трассам**, особенно карточку, избранное, рекомендации и dashboard; batch-выборка уже используется в ленте.
6. **Профилировать клиента на слабом Android/Slow 4G**; применять виртуализацию и мемоизацию при подтверждённом росте DOM или времени рендера.
7. **Аудировать npm/Python зависимости инструментами** включая optional groups; удалять только доказанно неиспользуемые прямые зависимости.

## Ограничения аудита

Это аудит исходников и конфигурации плюс read-only production-снимок, а не нагрузочный прогон. Позже запущен локальный backend набор: 102 теста прошли; TypeScript `tsc --noEmit` прошёл. Не выполнялись нагрузочный тест, Lighthouse/Chrome профилирование и полный замер CDN заголовков. Приоритеты выше — план дальнейшей валидации, а не утверждение, что все перечисленные оптимизации нужны независимо от измерений.

### Production PostgreSQL

Прямое соединение было read-only, `statement_timeout=12–15s`. Получены следующие результаты:

| Проверка | Результат |
|---|---|
| Сервер/объём | PostgreSQL 17.4, база 257 MB, лимит 60 соединений. |
| Основная таблица | `listing`: около 49.4 тыс. строк (48,287 active в статусной агрегации), 7.4 тыс. dead tuples; autovacuum последний раз прошёл 10.11 14:31 UTC. |
| Соединения | 11 видимых сессий; самая старая idle transaction около 0.36 с. Признака исчерпания пула в снимке нет. |
| Кэш страниц БД | Buffer hit ratio 96.66%. |
| EXPLAIN ANALYZE | Популярная лента 0.205 мс, make+year фильтр 3.489 мс, сортировка цены 2.016 мс, `%bmw%` поиск 0.875 мс на текущем объёме; планы используют `listing_active_published_idx`/`listing_active_price_idx`. Это один прогретый снимок, не нагрузочная гарантия. |
| Долгие SQL | `pg_stat_statements` не установлен, поэтому накопленные 4,831 temp files / 45.9 GB temp writes и 2 deadlocks нельзя приписать конкретным запросам или интервалу. Нужны `pg_stat_statements` и трассировка. |
| Наблюдаемость сборщика | `collector.status=running`; heartbeat свежий. Последние прогоны каждые ~2 минуты, 2 страницы, 10–18 с; ошибок в последних пяти прогонах нет. |

Сравнение с API показало разрыв: прямые прогретые SQL-планы занимают 0.2–3.5 мс, тогда как Railway HTTP-запросы списка с холодными/редкими фильтрами заняли 1.5 с. Это указывает на задержку вне собственно плана PostgreSQL — возможны DB pool checkout/check ping, межрегиональная сеть, сериализация, Redis или cold worker. Без `pg_stat_statements`, Railway logs и server-side timing точную причину не определить. Для роста до миллионов объявлений надо проверять запросы с нормальным объёмом и реальными фильтрами, прежде чем добавлять индексы: текущий объём слишком мал для честной оценки масштабирования.

### Что ещё не проверено

SQL/схема и публичные endpoints проверены, но Railway service logs/variables, Vercel project config, backup/restore и нагрузка при concurrency не доступны из этого окружения. Railway CLI аварийно завершается (код 134). `pg_stat_statements` отсутствует. Production DDL не менялся.

Отдельный security snapshot и найденные права `anon` задокументированы в [`SECURITY-audit.md`](SECURITY-audit.md). Подготовлена блокировка grants; production применит её только после review и подтверждения владельца проекта.
