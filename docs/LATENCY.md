# Горячий путь: от публикации объявления до сообщения в чате

Требование: как только объявление появилось на площадке — поймать его как можно
быстрее, обработать и прислать пользователю. Этот документ — про задержку,
а не про полноту данных. Полнота (описание, все фото, VIN) догоняется отдельно
и на скорость пуша не влияет.

## Метрика

```
createdAt (площадка)  ──►  detected_at (мы увидели)  ──►  sent_at (Telegram принял)
        └──────────── lag_publish_to_detect ───────────┘ └── lag_detect_to_send ──┘
```

Замерено (10 минут поллинга раз в 10 секунд, см. «Замеры»):

| Метрика | p50 | p90 | Комментарий |
|---|---|---|---|
| `lag_publish_to_detect` | **~83 с** | ~107 с | почти целиком — задержка индексации площадки |
| `lag_detect_to_send` | **~3 с** | < 8 с | наш участок, полностью под контролем |
| **`lag_publish_to_send`** | **~90 с** | ~120 с | пол — не наш |

Главный вывод замера: **площадка сама показывает объявление с задержкой
~40–110 секунд после `createdAt`**, причём пачками (раз в 1–2 минуты). Быстрее
неё не увидит никто — включая её собственные e-mail-уведомления. Наша задача —
не «победить площадку», а **не добавить к её задержке больше 15 секунд**: в этот
момент объявление только появилось на сайте, и мы уже шлём пуш.

## Бюджет задержки

| Этап | Время | Комментарий |
|---|---|---|
| Индексация на площадке | **40–110 с** | их пайплайн, пачками раз в 1–2 мин |
| Поллинг выдачи | 0–15 с | интервал, половина в среднем |
| HTTP: 2 страницы (brotli) | 1.5–3 с | 182 КБ каждая |
| Разбор JSON (`__NEXT_DATA__`) | ~40 мс | 1.7 МБ текста |
| Дифф id | < 1 мс | Redis SET |
| Матчинг подписок | < 5 мс | в памяти процесса |
| Запись в Postgres | 5–10 мс | не блокирует отправку |
| Telegram `sendPhoto` | 0.3–0.8 с | их API |
| **Итого наш участок** | **≈ 3–4 с** | после того как увидели |

## Решение 1. Уведомлять по данным выдачи, карточку — потом

В выдаче уже есть всё, что нужно для фильтра и для сообщения:

```
make, model, year, mileage, fuel_type, gearbox, engine_capacity, engine_power,
price, currency, city, region, seller type, thumbnail (x1/x2), createdAt, url
```

Карточка нужна для описания, VIN, полного набора фото, точных групп параметров.
Это **обогащение**, а не условие отправки.

```
новая строка выдачи ──► match ──► sendPhoto ──► готово (2–3 с)
                            │
                            └──► очередь обогащения ──► карточка ──► UPDATE (секунды-минуты)
```

Если ждать карточку, каждая новая машина добавляет 0.7 МБ загрузки и 0.5–1 с
разбора в критический путь. При ~5–7 тыс. новых в сутки это ещё и риск очереди:
детали отстают — пуши встают. Разделение снимает связку.

## Решение 2. Поллинг: страница 1 каждые 15 секунд, страница 2 раз в минуту

Замер показал: за 10 минут в окне первых двух страниц появилось **196 новых id**,
из них **136 — «поднятые» старые объявления** (возраст от часа до 25 дней),
и только 60 — действительно свежие (созданы в пределах часа). Свежих — около
**5 в минуту** (~7 тыс. в сутки).

Отсюда схема:

- страница 1 (32 объявления) — каждые 15 с: даже если 13 слотов заняты
  «поднятыми», остаётся 19 мест, а пачка новых за 15 с — единицы;
- страница 2 — раз в 60 с, как страховка на утренние всплески и на случаи,
  когда «поднятых» больше обычного;
- 5 760 + 1 440 ≈ **7 200 запросов в сутки**, ~1.6 ГБ трафика в brotli.

**Почему не чаще.** Площадка обновляет выдачу пачками раз в 1–2 минуты.
Поллинг чаще 10–15 с не ускорит пуш — только добавит запросов. Если замеры
на другом рынке/времени покажут более частые пачки, интервал можно уменьшить.

## Решение 3. Правило свежести: не пушить «поднятые» объявления

Это самое важное следствие замера. В выдаче постоянно всплывают объявления
с `createdAt` недельной и месячной давности — продавцы платят за «поднятие».
Если пушить по факту «мы увидели впервые», пользователь получит старьё.

Правило:

```
пушить, только если  createdAt > now − 6 часов
«поднятые» (старше)      → обновить last_seen, в БД оставить, пуша нет
```

6 часов — настраиваемый параметр. Причина не в осторожности: за 10 минут
наблюдения «поднятых» было в 2.3 раза больше, чем свежих (136 против 60).

## Решение 4. Состояние «что уже видели» — в Redis

```
SADD seen:otomoto <id>          # O(1), TTL 14 дней
```

Postgres не опрашивается на каждом объявлении. Раз в сутки — сверка Redis ↔ БД.
Идемпотентность прикрывает рестарты: `unique(user_id, listing_id, kind)`.

**Почему это критично:** выдача нестабильна между запросами — замечено, что
максимальный `createdAt` иногда откатывается назад, то есть один и тот же
запрос в разные секунды возвращает разные наборы. Значит «увидели» — это
состояние, которое нужно хранить, а не выводить из текущей страницы.

## Решение 5. Матчинг — в памяти, без SQL на каждое объявление

Подписок десятки-сотни, они меняются редко. Держим в процессе индекс:

```
by_make: {"bmw": [sub1, sub7], "audi": [sub3], ...}
```

Новое объявление → берём список подписок по марке (и по «любой марке») →
прогоняем критерии в Python. Это микросекунды. Postgres — только для записи
и для восстановления состояния после рестарта (и для Mini App-запросов).

SQL-матчинг «JOIN subscriptions ON criteria @> ...» на каждое объявление —
это 5–20 мс и лишняя нагрузка; оставляем как резервный путь.

## Решение 6. Отправка

- `sendPhoto` по URL миниатюры (640×480 с их CDN). Telegram сам скачивает фото —
  нам не нужно его проксировать.
- Если Telegram не смог забрать URL (CDN отдаёт только «своим») — fallback:
  скачиваем миниатюру сами (~50 КБ) и отправляем файлом. +0.3 с, зато надёжно.
- Ошибка `429` — `retry_after` из ответа, повтор из очереди, не в цикле.
- Идемпотентность: `unique(user_id, listing_id, kind)` — рестарт бота
  не приводит к повторному пушу.

## Что может сломать горячий путь

| Сбой | Признак | Реакция |
|---|---|---|
| Площадка начала отдавать 429/403 | серия ошибок в `crawl_run` | backoff до 60 с, алерт, деградация интервала |
| Изменилась структура `__NEXT_DATA__` | 0 объявлений за 10 минут днём | алерт, стоп поллинга, контрактный тест на фикстуре |
| Очередь деталей отстаёт | растёт `queue:detail` | не влияет на пуши; отдельный воркер, отдельный лимит |
| Telegram 5xx | ошибки `sendPhoto` | ретрай 3 раза с паузой, затем `sendMessage` без фото |
| Рестарт сервиса | — | состояние в Redis/БД, подписки перечитываются, пропусков нет |
| Всплеск «поднятых» | доля свежих падает | правило свежести отсекает; алерт, если свежих 0 больше 30 мин |

## Мониторинг

Пишем по каждому объявлению: `created_at`, `detected_at`, `sent_at`.
Метрики: p50/p95 `lag_publish_to_detect` и `lag_detect_to_send`, доля свежих
среди новых id, число поллингов без новых id подряд, ошибки, глубина очередей.

Алерты:

- **0 новых объявлений за 10 минут в рабочее время** — главный сигнал,
  что мы ослепли (сменилась вёрстка или нас заблокировали);
- ошибки поллинга > 5% за 15 минут;
- p95 `lag_detect_to_send` > 15 с;
- доля свежих (`createdAt` моложе 6 ч) среди новых id < 20% дольше часа —
  возможно, площадка поменяла механику выдачи.

## Замеры (05.11.2026, 11:41–11:52 Europe/Warsaw)

Поллинг 10 секунд, 2 страницы, скрипт `scripts/latency_probe2.py`.

- **196 новых id за 10 минут**, из них свежих (моложе часа) — 60, «поднятых» — 136.
- **Свежих ~5 в минуту** (~7 тыс./сутки).
- Лаг `createdAt → мы увидели` для свежих: **p50 83 с, p90 107 с, max 115 с**
  (n = 30 объявлений с лагом ≤ 3 минут).
- Максимальный `createdAt` в выдаче растёт **ступенями раз в 60–120 с**:
  например, 11:47:13 → 11:48:29 → 11:49:39. Это индексация пачками.
- **Выдача нестабильна:** в 11:44:12 и 11:45:32 максимальный `createdAt`
  откатился назад (11:43:24 → 11:42:05 → 11:43:24). Один и тот же запрос
  в разные секунды отдаёт разные наборы.
- **Brotli:** 1.76 МБ → **182 КБ** (`Content-Encoding: br`, в 9.7 раза).
- `Cache-Control: no-store`, `ETag` меняется на каждый ответ — `If-None-Match`
  экономии не даст. Экономим только сжатием.

## Что сознательно не делаем

- **Не идём в `/api/` и GraphQL-подписки.** В `robots.txt` они запрещены
  (`Disallow: /api/`, `/ajax/`), а в выдаче есть поле `subscriptionKey` —
  соблазн подписаться на живой поток велик, но это уже не «страницы, которые
  разрешены». Держимся HTML-выдачи.
- **Не батчим в instant-режиме.** Дайджест — только если пользователь сам
  его включил; иначе задержка.
- **Не считаем аналитику в горячем пути.** Медианы по когортам — из кэша
  (Redis), пересчёт ночью. Нет кэша — отправляем без оценки «ниже рынка»,
  досчитываем позже.

## Критерий готовности (фаза 2)

- p50 `lag_detect_to_send` < 5 с, p95 < 15 с (наш участок);
- p50 `lag_publish_to_send` < 2 мин, p95 < 3 мин (с учётом индексации площадки);
- сверка за 24 часа: все свежие id, появившиеся в выдаче, есть в БД
  (пропусков нет);
- ни одного повторного пуша на одно объявление и ни одного пуша по «поднятому»;
- алерт «0 новых за 10 минут» проверен искусственно (сломанный селектор).
