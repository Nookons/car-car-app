# Ранжирование: один «котёл» интереса

Объявление ранжируется по тому, что с ним **делают люди**, а не по тому, из
какого источника оно пришло. Поиск, лента («ТикTok»-подобная) и карточка пишут
в одни и те же счётчики, поэтому подборка учится на любом действии, а не только
на ленте.

## Что считается

| Сигнал | Кто пишет | Смысл |
|---|---|---|
| `impressions` | поиск (`/api/listings`, в т.ч. ответ из Redis), лента (`/api/feed`) | «показали в выдаче» |
| `views` | `POST /api/listings/{id}/view`, открытие карточки | «открыл» — один раз в день на пользователя |
| `favorites` | избранное | «сохранил себе» — осознанный выбор |
| `likes` | реакция | быстрый тап |
| `comments` | комментарий | обсуждение |
| `reposts` | репост | «поделился» |

Все шесть лежат в `listing_stat` (`carcar/schema.sql`), миграция —
[`db/migrations/20261113_engagement_pool.sql`](../db/migrations/20261113_engagement_pool.sql).

## Формула

Одна на всё приложение — `listing_engagement_score()` в БД; `score`
пересчитывает триггер `listing_stat_score` при любом изменении счётчиков.
Ручных формул в коде больше нет: писатель не может посчитать по-своему.

```
score = ln(1 + views + 5·favorites + 2·likes + 3·comments + 4·reposts)
      + 4 · (views + 1) / (impressions + 10)
```

Два слагаемых решают две разные задачи:

1. **Популярность** под логарифмом. Десятый лайк весит меньше первого, поэтому
   раскрученное объявление не уезжает в вечный топ и не давит новое.
2. **CTR** — доля открытий от показов. Это и есть «открыли важнее, чем
   увидели»: объявление, которое показали 100 раз и не открыли, проигрывает
   тому, что показали 10 раз и открыли 3. Сглаживание `+1/+10` не даёт одному
   показу с одним открытием изобразить 100 % интереса.

## Свежесть

Порядок в ленте — `score / (1 + возраст_в_днях / 21)`:

- через три недели объявление стоит вдвое дешевле, через полгода — в 9–10 раз;
- но не исчезает: рынок не должен состоять только из вчерашних машин;
- новый источник или «холодное» объявление без сигналов не проигрывает
  в ноль — оно просто сортируется по дате.

## Персонализация

Вкус пользователя (`MiniAppRepo._taste`) собирается из:

- сохранённых подписок (фильтры) — вес 3;
- просмотров — 2;
- лайков — 4;
- **избранного — 5** (осознанный выбор сильнее случайного тапа).

Дальше `for_you` фильтрует по марке/кузову/цене и сортирует тем же общим
порядком «интерес → свежесть», а не по дате, как было раньше. Просмотренные
объявления в `for_you` не повторяются.

## Чего здесь пока нет

- Коллаборативной фильтрации («кто смотрел это, смотрел ещё…»). Сейчас
  избранное влияет на общий score, но не строит соседство объявлений.
- Скользящего окна: счётчики накопительные, «интерес за 30 дней» отдельно не
  считается — свежесть гасит старые всплески в порядке выдачи.
- Учёта показов в блоке «похожие» и в карточке — туда сигнал не пишется.
- Защиты от накрутки: один и тот же пользователь может показать объявление
  повторно, показы не дедуплицируются по пользователю (открытия — да,
  один в день).
